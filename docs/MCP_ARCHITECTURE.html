Cardio4Cities · engineering notes

MCP in Cardio4Cities

The Model Context Protocol is a contract between an AI application and the capabilities it uses. These notes explain the protocol from first principles, then walk through how our research agent now gets its search and its prompts from an MCP server of its own, and what we did to keep every guarantee the agent made before.

  • MCP spec 2026-07-28
  • Python SDK mcp 2.3.0
  • E-15 phase 1 · BD-60
  • 19 October 2026

Part 1 · MCP concepts

The problem MCP solves

Every AI application needs to reach things outside the model: search, files, databases, internal APIs, prompt libraries. Without a shared contract, each application writes its own integration for each capability, and each integration has its own way to describe inputs, report errors and authenticate. Three applications and three capabilities need nine integrations, and the tenth capability needs three more.

MCP replaces that with one protocol. A capability is wrapped once as an MCP server; an application speaks MCP once through an MCP client. Any client can then use any server, and the description of each capability (its name, its input schema, what it returns, whether it changes anything) travels with it.

The protocol does not make a capability safe or correct. It makes it describable and reachable. Whether a tool's output can be trusted, whether a call should be allowed, and what it may cost stay the job of the people who build the client and the server. Most of Part 2 is about those decisions.

Host, client, server

MCP names three roles. They are easy to blur, and the distinction matters for security: the host decides what the model sees and what the user must approve; the server decides what it will do for whom.

RoleWhat it isIn Cardio4Cities
HostThe AI application. It owns the conversation or workflow, decides which servers to connect to, and decides what reaches the model.The agent: the API process that runs research workflows and answers questions. An outside assistant or IDE is a host too.
ClientThe connector inside a host that speaks MCP to one server.The mcp adapters in app/adapters/mcp/, built on the SDK's Client.
ServerA program that offers tools, resources and prompts over MCP.The tools-and-prompts server in app/mcp_server/, on 127.0.0.1:8100.

A single host can hold many clients, one per server. Our agent holds one: the server that serves search and prompts. The stores and the model providers are not MCP servers; the agent talks to them directly through its own adapters.

What a server offers

A server can expose three kinds of thing. The difference between them is who decides when they are used.

PrimitiveChosen byWhat it is forOur server
ToolsThe model (through the host)Actions and queries with typed inputs and outputs: search, look something up, change something.search_links live
PromptsThe user or the applicationReusable message templates, listed by name with optional arguments.One per model role: planner, extractor, checker, classifier, answerer, reporter live
ResourcesThe applicationReadable data addressed by URI: files, records, documents.None yet

Clients can offer features back to servers. In the current revision most of these are being retired, which is a deliberate simplification of the protocol:

Client featureWhat it didStatus in 2026-07-28
SamplingThe server asks the client's model to generate text.deprecated call model APIs directly instead
RootsThe client tells the server which directories it may use.deprecated pass paths as tool arguments or configuration
LoggingThe server streams log messages to the client.deprecated log to stderr or OpenTelemetry
ElicitationThe server asks the user for input mid-request.active now through multi round-trip requests

Our server uses none of the client features. The agent never lets a server drive its model, which would be a second way for untrusted text to reach a prompt.

The wire

MCP messages are JSON-RPC 2.0: a request has a method and parameters, a response has a result or an error. Two transports carry them.

TransportHowWhen to use it
stdioThe host starts the server as a child process and writes JSON-RPC to its stdin, reading replies from stdout.A local server used by one host. Only that host can reach it.
Streamable HTTPEach request is an HTTP POST to one endpoint; the reply is JSON or a short event stream.A server shared by several hosts or processes, local or remote. Ours: one server used by the API, research runs and outside clients.

Here is a real call from our agent, with the two headers the current revision requires on every Streamable HTTP POST. The city is the project's fictional test city.

Request · POST /mcp

Authorization: Bearer <MCP_AGENT_TOKEN>
Mcp-Method: tools/call
Mcp-Name: search_links

{
  "jsonrpc": "2.0", "id": 7, "method": "tools/call",
  "params": {
    "name": "search_links",
    "arguments": { "query": "Halden Bay hypertension programme", "lang": "en", "limit": 10 },
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {}
    }
  }
}

Response · 200

{
  "jsonrpc": "2.0", "id": 7,
  "result": {
    "resultType": "complete",
    "isError": false,
    "structuredContent": {
      "links": [
        { "url": "https://health.halden-bay.test/hypertension", "title": "Blood pressure programme",
          "snippet": "…", "rank": 1 }
      ]
    },
    "content": [ { "type": "text", "text": "{\"links\": [ … ]}" } ]
  }
}

structuredContent is the typed result that code reads; content is the same result as text for hosts that only show text to a model. A tool that fails returns isError: true with an explanation in content, rather than a protocol error, so the model or the code can react to it.

The 2026-07-28 revision: stateless MCP

Earlier revisions opened a session with an initialize handshake and tracked it with an Mcp-Session-Id header. The current revision removes both. Every request stands alone and carries what the server needs to know about the client in _meta. This is the change that shaped our design most.

What changedWhat it means for us
No sessions, no initialize; version and capabilities in each request's _meta.The server runs in stateless mode. Each agent call opens a short-lived client over a shared HTTP connection, and nothing has to outlive the task that made the call.
server/discover advertises versions and capabilities.The SDK client calls it first; it appears in our audit log as the first line of every connection.
Cross-call state uses server-minted handles passed as tool arguments.Phase 2's per-run "collection" handle follows this pattern (proposal).
Multi round-trip requests replace server-initiated requests.The server can never call back into the agent in the middle of a call, which is why phase 2 needs a hold-and-settle budget.
Long-running work moved to an optional tasks extension.Not needed in phase 1: a search takes seconds.
Mcp-Method and Mcp-Name headers on every POST.The access gate logs which method and tool each request was for without parsing the body.
List results carry cache hints; tools should be listed in a fixed order.Our tool and prompt lists are deterministic (prompts sorted by role).

Anatomy of a tool

A tool is described by what a host sees in tools/list. Ours, as the server lists it:

{
  "name": "search_links",
  "title": "Search the web for links",
  "description": "Web search that returns links only (URL, title, snippet, rank). Snippets rank links
                  and are never evidence. Read-only; counts against your daily search quota.",
  "inputSchema":  { "query": string, "lang": string = "en", "limit": integer = 10 },
  "outputSchema": { "links": [ { "url", "title", "snippet", "rank" } ] },
  "annotations": { "readOnlyHint": true, "destructiveHint": false,
                   "idempotentHint": false, "openWorldHint": true }
}
  • The description is for a model. An outside host's model decides when to call the tool from this text, so it states the one rule that matters most: a snippet is never evidence.
  • The schemas are for code. The SDK builds them from the Python signature and the Pydantic return type, and validates both directions.
  • Annotations are hints, not guarantees. A host may use them to skip a confirmation for read-only tools. A host must not trust them from a server it does not trust, and our server enforces its own limits whatever the hints say.
  • idempotentHint: false because the same query can return different links tomorrow, and each call spends from a quota.

Anatomy of a prompt

A prompt has a name, a description, optional arguments, and the messages it returns from prompts/get. Two details shaped how we serve ours.

  • Messages are user or assistant. MCP prompt messages have no system role. Our prompts are system prompts, so each is served as one message that the agent uses as its system text.
  • A prompt result carries no metadata. The version therefore travels in the prompt's description, in one fixed form the agent parses: version=checker@v4+82603e11.
# prompts/list (one of six)
{ "name": "checker", "title": "Check one claim against its passage",
  "description": "System prompt of the checker role, as one message. version=checker@v4+82603e11" }

Security model

MCP joins three parties that do not fully trust each other: the host and its user, the server, and whatever the server reaches. The specification's security guidance names the attacks that follow from that, and the ones below are those that apply to a server like ours.

RiskWhat goes wrongWhat the specification asks
Tool poisoningA server hides instructions in a tool's description or results; the host's model follows them.Hosts treat server metadata and results as untrusted unless the server is trusted.
Prompt injection through resultsWeb text returned by a tool carries instructions to the model that reads it.Treat tool output as data; keep consent and approval in the host.
Token passthroughA server accepts a token meant for another service, or forwards the caller's token downstream."MCP servers MUST NOT accept any tokens that were not explicitly issued for the MCP server."
State handle hijackingSomeone guesses or steals another caller's handle.Servers "MUST NOT treat possession of a state handle as authentication"; bind handles to the caller.
Local server reachable by othersA web page or another process on the machine calls a local HTTP server, for example through DNS rebinding.Use stdio, or restrict HTTP access with an authorization token; validate Host and Origin.
Over-broad accessOne credential opens everything.Least privilege; separate scopes per kind of operation.

Remote servers use OAuth 2.1, with the server acting as a resource server that validates tokens issued for it. Our server is local only, so phase 1 uses a bearer token per client on loopback, which the guidance allows for local HTTP servers. A deployed server would need OAuth first, and the deployed profile refuses ours until then.

Part 2 · Our implementation

What moved, and what did not

The owner's direction was to move the agent's tools and prompts out of code and behind an MCP server the agent calls, open to outside MCP clients too. Phase 1 moved the two pieces that could move without touching any of the agent's guarantees.

PieceWhere it is nowWhy
Search (links only)MCP serverStateless and narrow. The server enforces "links only", so no caller can switch on a provider's page-content feature.
Prompts (six roles)MCP serverFits MCP prompts. The agent checks every served version against its own code (see Prompts at start-up).
Crawl gate, fetching, parsingphase 2A bare fetch tool would bypass the crawl gate, which must decide before any content request. They move together, as one gated collector.
Structured data (official APIs)phase 2Its requests use the collector's pinned fetch path, and the stored bytes are re-parsed to verify facts, so it moves with fetch.
Postgres, Qdrant, Neo4jstays in the agentThese are data, not tools. Answers re-check every candidate against Postgres directly.
Model calls, the checkerstays in the agentNot tools. Sampling, the MCP way to route model calls through a server, is deprecated.

Architecture

Three boundaries carry the design:

  • Process boundary. The server is a separate process with its own composition root (app/mcp_server/main.py), started by poe mcp or by poe dev before the API. Nothing in the agent's core can import it; an import-linter contract enforces that.
  • Network boundary. The server binds to loopback only, and the settings refuse any other host. Every request must carry a bearer token and pass the Host and Origin checks.
  • Trust boundary. The agent trusts its own server's prompts only after verifying them against its own code, and treats search results exactly as before: links to rank, never evidence.

MCP as an adapter

The agent is built as ports and adapters: core code depends on interfaces such as SearchPort, and adapters implement them. MCP fits in as one more adapter. The workflow's search node calls search(query, lang, limit) exactly as it did, and the container decides which adapter answers.

# app/container.py: the agent reaches search through the server when configured (BD-60)
search_provider = "mcp" if "search" in config.mcp.agent_uses else config.search.provider
container.search = build("search", search_provider)
# app/adapters/mcp/search.py: the same port, over the protocol
class McpSearch:
    async def search(self, query, lang, limit=10) -> list[SearchHit]:
        data = await self._caller.call_tool("search_links", {"query": query, "lang": lang, "limit": limit})
        return [SearchHit.model_validate(link) for link in data["links"]]

This has three consequences worth stating plainly:

  • The budget still holds. The research workflow reserves from its budget ledger before every search, in the node, before the adapter is called. Moving search behind MCP did not move that check.
  • Failures look the same. A refused token, a dead server or a tool error all become ProviderUnavailableError, the error every search adapter raises, so the workflow's handling did not change.
  • One switch. TOOLS_VIA_MCP=1 routes search and prompts through the server; poe dev sets it. With TOOLS_VIA_MCP=0 the agent runs in-process, which is also how most tests run.

One search, end to end

Two sets of limits apply to every search, on purpose. The agent's budget ledger caps what a research run may spend. The server's limits (calls per minute, searches per day, query and limit bounds) cap what each caller may spend, and they are the only limits an outside client meets, because outside callers do not spend from any run's budget.

Prompts at start-up

A prompt is more than its text. What the model sees is the system text plus the user message that the role's context.py builds from typed data, escaped by safety.py; what comes back is parsed by the role's schema.py. The version stamped on every claim, verdict and answer covers all four:

prompt_version = "<role>@v<n>+" + sha256(text + schema.py + context.py + safety.py)[:8]
               # e.g. checker@v4+82603e11

The server owns the text; the agent keeps the schema, the context builder and the escaping, because those are code that runs where untrusted page text enters. So at start-up the agent reads all six prompts and recomputes each version itself.

All six are checked or none is installed. The check refuses three cases: text changed without a new version, a version other than the one this code runs, and a role the server did not serve. Prompts are read once, so a research run can never change prompts halfway through.

# app/prompts/loader.py (abridged)
def use_served(served):
    for role, text, prompt_version in served:
        expected = _version_of(role, CURRENT[role], text)   # local schema, context, safety
        if prompt_version != expected:
            raise PromptMismatchError(...)                  # the app does not start
    if missing := set(CURRENT) - served_roles:
        raise PromptMismatchError(f"not served: {missing}")
    install(checked)                                     # load_prompt() now returns these

The first live start-up served exactly the versions the prompt files produce (for example checker@v4+82603e11), so moving the prompts behind MCP changed nothing that is stamped on the agent's outputs.

Who may call, and how much

Each caller is an entry in the profile's mcp.clients list with its own token and limits. A client whose token is not set cannot connect at all.

ClientTokenCalls per minuteSearches per dayWho it is
agentMCP_AGENT_TOKEN6002,000Our API and research runs (also capped by each run's budget)
externalMCP_CLIENT_TOKEN30100An outside MCP client: another assistant, IDE or agent

The access gate compares tokens in constant time and answers 401 with a WWW-Authenticate header when the token is missing or unknown, and 429 when a caller exceeds its calls per minute. The search tool counts the daily quota. Every request leaves one audit line; arguments and results are never logged, because a query can carry a city name and results carry web text.

Audit log, from the first live run

mcp prompts/get checker by agent: 200 in 2 ms
mcp tools/call search_links by agent: 200 in 3143 ms
mcp tools/call search_links by external: 200 in 873 ms

Threats and controls

ThreatControl in our server
Another process or a web page calls the local serverBearer token per client; loopback bind enforced by settings; Host and Origin allow-lists against DNS rebinding.
A caller spends without limitCalls per minute and searches per day per caller; query length, language format and link limit bounded by config.
A caller turns on page content in searchThe tool calls the links-only adapter; there is no argument that changes the mode.
A served prompt drifts from the code that uses itStart-up recomputes every version against local schema, context builder and safety rules, and refuses on any difference.
Search results steer a modelUnchanged agent rule: titles and snippets only rank links and never become evidence or prompt text; pages are read through the crawl gate.
Token passthroughThe server accepts only its own configured tokens and never forwards them; the SearXNG call carries no caller credential.
Secrets or web text in logsAudit lines hold caller, method, tool name, status and time only.
Exposure beyond this machineRefused with APP_ENV=deployed until the server has OAuth.

An outside client's own model reads whatever our tools return. Search results are links and short snippets today. When collection tools arrive in phase 2, page text returned to an outside client must be marked as untrusted web content, and those tools stay agent-only unless the owner opens them.

How it is tested

  • The shared search contract. The same tests that every search adapter must pass (links, titles and snippets only; the limit kept; no results; provider failures mapped to the port error) now run against McpSearch too, over the real MCP protocol, in-process, with SearXNG behind the server.
  • The server. The tool list and its hints; every prompt served with its version; search bounds; the daily quota; a call without a token refused.
  • The prompt check. Served prompts install unchanged; text changed without its version, an older version and a missing role are each refused, and a refused set leaves the prompt files in use.
  • Over real HTTP. One test runs the server on a loopback port: the agent searches and reads prompts with its token, an unknown token is refused, and a request with a foreign Host header is rejected.
  • Configuration. TOOLS_VIA_MCP=1 needs the agent's token; the deployed profile refuses the server; the server refuses to start with no client token.

No test reaches the internet. The full suite (1,190 tests) passes, and continuous integration ran it again before the merge.

Running it

uv run poe up      # stores and SearXNG (Docker)
uv run poe dev     # MCP server :8100, then the API :8000 through it, then the web app :3000
uv run poe mcp     # the MCP server alone
TOOLS_VIA_MCP=0 uv run poe dev   # everything in-process, no MCP server

To connect another MCP client on this machine, give it the endpoint http://127.0.0.1:8100/mcp and the header Authorization: Bearer followed by the value of MCP_CLIENT_TOKEN from .env. It will see one tool and six prompts, and its calls are logged as external.

Phase 2 and beyond

Phase 2 is a proposal awaiting the owner's decisions (docs/design/MCP_PHASE2.md). It moves the crawl gate, fetching, parsing and official-API requests into the server, making the server the only part of the system that touches the web.

ProblemProposed answer
The collector keeps per-run state (robots.txt, certificate chains, per-site spacing).A server-minted collection handle per run, random, expiring, bound to the caller's token.
The server cannot ask the agent's ledger for budget mid-call.Hold and settle: hold a per-call allowance before the call, give back what was not used.
Stored bytes must be the bytes parsed.Raw bytes returned with their SHA-256; the agent checks the hash and stores the snapshot.
The agent still parses snapshots for verification and reindexing.A parser version checked at start-up, like prompt versions.

Beyond that, a deployed server would add OAuth 2.1 with tokens issued for this server only, and per-client tool allow-lists so outside clients see only what they are meant to use.

Ground rules

What this build suggests for putting MCP inside an agentic system, rather than only in front of one:

  1. Put MCP behind a port. Make the MCP client one adapter among others, so the workflow cannot tell the difference and every existing contract test applies to it.
  2. Keep the checks on the agent's side of the wire. Budget reservation, the crawl gate's decision and the evidence rules belong to the code that answers for the outcome, not to a server it calls.
  3. Never expose a capability that skips a gate. If a tool would let a caller bypass a rule the system depends on, move the rule into the tool with it, or do not ship the tool.
  4. Version what you serve, and verify it where it is used. A served prompt is safe only if the client proves it matches the code that builds its input and parses its output.
  5. Treat annotations as hints and enforce limits yourself. Read-only hints help hosts; tokens, quotas and bounds protect the server.
  6. Give every caller its own identity and budget. Outside callers do not spend from your run budgets, so the server's limits are their budget.
  7. Audit the call, never the content. Log who called what and how it ended; leave arguments and results out of logs.
  8. Design for the stateless protocol. Pass state as server-minted handles bound to the caller, and never let a handle stand in for authentication.
