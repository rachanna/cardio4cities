Context is everything the model can see when it answers

Context engineering is deciding, for every model call, what the model sees, in what form and order, how much of it, and what it must never see.

A language model has no memory between calls and no view of your system. Whatever it knows about the task arrives in one request: the instructions, the data, the output format, and anything carried over from earlier steps. That request is its whole world. If a fact is not in it, the model either does without it or invents it.

Prompt engineering is about the wording of instructions. Context engineering is about the system that fills the request: which records are retrieved, how a long page is cut, what an earlier step hands to a later one, where untrusted text sits, and what stays out on purpose.

Role by role: the decisions behind each context

Extractor: choose the right slice of a long page

A page can be hundreds of thousands of characters. Sending all of it costs money, dilutes attention, and invites the model to pick the wrong figure. So code chooses what the extractor reads.

Pages for the question: those naming the city first; once a wider-area fact is held, at most 1 page that never names the city
Cut each page into 12,000-token windows with 500 tokens of overlap
Score each window by whole-word hits on the city's names and the question's words
Keep the best 4 per page, returned in document order
One call per window, wrapped as an untrusted <source>, with the allowed relation types listed so the model knows what code will drop

Telling the model which relation pairs are allowed is context engineering too: code drops any other pair, so a model that does not know the rule wastes its output on claims that can never survive.

Checker: independence comes from what it cannot see

Shown

  • The claim and its value as written
  • Labels in plain words: "the whole city or town", "prevalence, method not stated"
  • "not stated" wherever a label is empty
  • The passage around the quote, ±600 characters, located by code
  • The passage stating a label found elsewhere, such as the survey period in the methods

Withheld

  • The extractor's prompt, output and reasoning
  • Other claims and other sources
  • The research question it was meant to answer
  • The rest of the page

The checker cannot be persuaded by the framing that misled the extractor, because that framing never reaches it. The builder build_user_message takes exactly these inputs, so nothing else can be added by accident. Two lessons from the golden set are built in: codes such as city_wide were read as mismatches, so labels are written in plain words; and a period of "2024" stays "2024", never an invented "2024-01-01 to 2024-12-31".

Planner: carry forward what was learned, not what was said

A re-plan gets one line per unfilled question: its status, the queries tried, the gap note, and the sites that refused access. That is enough to try something different and to stop searching blocked sites, and nothing in it is page content the planner could mistake for a finding.

Classifier: decisions travel between turns, answers do not

A follow-up question ("and in 2023?") reuses the previous turn's classification: its questions, indicators and entities. It never receives the previous answer's text. An earlier answer is model output; feeding it back would let an error, or an abstention's wording, shape the next turn. The question itself sits in its own escaped tag: it is user input to classify, not an instruction.

Answerer: facts as data, with an ID on every line

The answerer sees no pages. It sees verified facts as data lines, each with a claim ID, the value as written, the area level in words, the period, the badge, the confidence and any contested partner. It must cite one ID per sentence, and code checks every number, place, name and year against those lines. Gap notes are context too: "not found" has to be in the context for the model to say it.

- [clm_…] FACT: In Halden Bay, 31.2% of adults aged 30-79 had hypertension | value 31.2%
  | describes the whole city or town (Halden Bay) | period 2024 | badge none
  | confidence High | slot S03 | contested_with: none

Report writer: linking prose only

Code assembles the report from stored facts. The model writes only introductions and analysis points from the facts and gaps it is given, and a post-check removes any sentence that adds something. Its context is designed so it has nothing to compute and nothing new to assert.

The build was context-engineered too

The coding agent that built this system works under the same constraint as the models inside it: it knows only what is in its context. So the repository is organised to give it the right material for each task and nothing that would mislead it.

Ground rules for agentic systems

General rules, each with where this project applies it.

  1. Build context in code, per call. Never let context accumulate as a running transcript; assemble exactly what this call needs from the stores.
    Here: six context builders, each a function with fixed inputs.
  2. Give each role only what its job needs. Need-to-know is a feature: it cuts cost and noise, and it creates independence.
    Here: the checker's restricted slice.
  3. Separate instructions from data. Fence untrusted text, escape anything that could pose as your tags, and treat model output derived from untrusted text as untrusted.
    Here: wrap_source, escape_untrusted, escaped claims and repairs.
  4. Make absence explicit. An empty field says "not stated"; gaps are listed; every vocabulary has an honest option for "the source doesn't say".
    Here: checker labels, gap notes, "method not stated" (BD-48).
  5. Write context in the reader's words. Labels, not codes; structure, not prose blobs; one fact per line with its ID.
    Here: LEVEL_WORDS, MEASURE_WORDS, fact lines.
  6. Bound it, then rank inside the bound. Fixed windows, caps and excerpt lengths; within them, the most relevant material first.
    Here: 12,000-token windows, best 4 by term hits, pages naming the city first, 8 facts.
  7. Keep state outside the model. Pass IDs between steps and resolve them in code; the store is the memory, not the context.
    Here: claim IDs in state and citations; Postgres re-validates every candidate.
  8. Carry decisions forward, not prose. Hand the next step what was decided and what failed, never the previous model's wording.
    Here: re-plan attempts and refused sites; classifier reuse without answer text.
  9. Constrain and check the output. Schemas, token ceilings and code checks before any output becomes another call's context.
    Here: structured outputs, quote matching, the post-check.
  10. Put stable material first. A fixed system prompt first, variable data last, so it caches and so each call reads the same way.
    Here: cached system prompts (BD-30).
  11. Version the context, not only the prompt. The code that builds a context changes behaviour as much as the wording does.
    Here: prompt versions hash the prompt, schema, builder and safety.py.
  12. Test context with golden sets, one change at a time. Measure each role on fixed cases, including attacks, before and after a context change.
    Here: extractor, checker, classifier and answerer golden sets with injected-instruction cases.
